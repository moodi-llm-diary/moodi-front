# GOAL — Moodi 모바일 퍼스트 반응형 전환 및 AI 기록 탐색 채팅 구현

## 0. 목표와 적용 범위

현재 Moodi의 데스크톱 디자인 방향과 다음 시각 원칙은 유지한다.

* ChatGPT·Notion 계열의 접이식 좌측 사이드바
* Apple 제품 디자인에서 참고한 절제된 색상과 재질감
* 중립색 중심의 일관된 surface 계층
* 단일 Moodi accent color
* Pretendard 기반의 한국어 타이포그래피
* 문서 중심의 블록 에디터
* 따뜻하지만 과도하게 장식적이지 않은 개인 일기 앱

이번 Goal에서는 기존 디자인을 다시 전면 교체하지 않는다.

다음 두 영역을 집중적으로 구현한다.

1. **모바일을 최우선으로 하는 반응형 UI**
2. **사용자의 과거 기록을 찾고 요약하고 연결하는 AI 채팅 탭**

기존 `ref_docs/goal.md`와 충돌할 경우 다음 우선순위를 따른다.

1. 사용자 데이터와 기존 비즈니스 로직의 안전성
2. 기존 `ref_docs/goal.md`의 디자인 시스템
3. 이번 문서의 모바일·AI 채팅 요구사항
4. 현재 구현된 임시 UI

---

# 1. 핵심 제품 방향

Moodi의 모바일 버전은 데스크톱 화면을 단순히 축소한 화면이 아니어야 한다.

모바일에서는 다음 경험을 제공한다.

* 한 손으로 주요 기능을 탐색할 수 있음
* 하단 네비게이션을 통해 핵심 화면으로 즉시 이동할 수 있음
* 햄버거 메뉴를 통해 최근 기록, 임시저장, 회고와 설정에 접근할 수 있음
* 작은 화면에서도 일기를 편안하게 읽고 작성할 수 있음
* 키보드가 열려도 작성 영역과 채팅 입력창이 가려지지 않음
* AI 채팅을 통해 자신의 과거 기록을 자연어로 검색할 수 있음
* AI 답변에서 어떤 기록을 근거로 사용했는지 확인할 수 있음
* AI가 사용자의 기록을 지어내지 않음

Moodi의 핵심 경험은 다음 세 가지다.

```text
기록한다.
찾아본다.
돌아본다.
```

AI 채팅은 별도의 부가 기능이 아니라, 사용자가 축적한 기록을 다시 활용하는 핵심 기능이다.

# 2. 작업 전 확인

작업을 시작하기 전에 다음을 조사한다.

1. 현재 앱 셸과 사이드바 구조
2. 현재 모바일 breakpoint와 media query
3. 모바일 하단 내비게이션 존재 여부
4. 전역 typography와 spacing token
5. `100vh` 사용 위치
6. fixed 또는 sticky 요소
7. 모바일 overflow 발생 가능 요소
8. 블록 에디터의 모바일 동작
9. AI 관련 기존 API, service, repository와 타입
10. 채팅 또는 메시지 관련 기존 구현
11. 기록 검색 API
12. 기록 요약 API
13. Markdown 렌더러 존재 여부
14. 사용자 일기 데이터 모델
15. 기존 인증과 사용자 식별 방식

AI API가 이미 존재한다면 해당 구조를 우선 재사용한다.

API가 없는데 존재한다고 가정하여 임의의 엔드포인트를 만들지 마라.

# 3. 전체 반응형 전략

다음 화면 구간을 기준으로 설계한다.

```text
Large desktop: 1440px 이상
Desktop:       1024px~1439px
Tablet:        768px~1023px
Mobile large:  430px~767px
Mobile:        390px 전후
Mobile small:  360px 전후
```

필요한 경우 실제 콘텐츠를 기준으로 breakpoint를 조정할 수 있다.

단순히 Bootstrap 또는 Tailwind 기본 breakpoint를 기계적으로 사용하지 마라.

## 원칙

* fixed pixel width보다 fluid width와 max-width를 우선한다.
* 주요 컨테이너에 `min-width: 0`을 적용하여 overflow를 막는다.
* `100vh`보다 `100dvh` 또는 적절한 fallback을 사용한다.
* 모바일 safe area를 지원한다.
* 가로 스크롤은 명시적으로 필요한 콘텐츠 외에는 발생하지 않아야 한다.
* desktop hover에만 의존하는 기능은 모바일 대안을 제공한다.
* 버튼, 메뉴, 팝오버가 viewport 밖으로 나가지 않아야 한다.
* 입력 필드의 모바일 폰트 크기는 16px 미만으로 낮추지 않는다.
* 모바일에서 마우스 hover를 전제로 한 블록 기능은 long press, tap 또는 메뉴로 대체한다.

# 4. 데스크톱 내비게이션 변경

현재 ChatGPT·Notion형 사이드바 컨셉을 유지한다.

AI 채팅을 사이드바의 주요 메뉴로 추가한다.

## 권장 순서

```text
새 기록

오늘
AI와 대화
모든 기록
캘린더
회고

작성 중인 기록
최근 기록

프로필
설정
```

`AI와 대화`는 보조 설정 메뉴가 아니라 `오늘`, `모든 기록`과 같은 수준의 핵심 메뉴다.

추천 아이콘은 하나의 기존 아이콘 세트에서 선택한다.

반짝이 이모지나 로봇 이모지를 사용하지 마라.

## AI 채팅 활성 상태

* Moodi accent soft background
* 아이콘과 텍스트 accent 적용
* 다른 메뉴와 동일한 활성 상태 규칙 사용

AI 메뉴만 별도의 화려한 그라데이션을 사용하지 않는다.

---

# 5. 모바일 상단 바

모바일에서는 데스크톱 사이드바를 숨긴다.

각 주요 화면에 공통 Mobile App Bar를 사용한다.

## 기본 구성

```text
[햄버거]     현재 화면 제목            [주요 동작]
```

예:

```text
오늘:
[메뉴]       Moodi                    [새 기록]

기록:
[메뉴]       기록                     [검색]

AI:
[메뉴]       Moodi AI                 [새 대화]

캘린더:
[메뉴]       2026년 7월               [오늘]

설정:
[뒤로]       설정
```

## 규격

* 높이: 52~60px
* safe area top 반영
* sticky 또는 fixed 사용 가능
* 콘텐츠와 겹치지 않음
* 중립적인 material surface
* 얇은 경계선 또는 매우 약한 blur
* 제목은 한 줄 ellipsis
* 아이콘 버튼 터치 영역 최소 44×44px

모바일 상단 바를 거대한 헤더나 랜딩 영역처럼 만들지 않는다.

---

# 6. 모바일 햄버거 드로어

햄버거 버튼을 누르면 왼쪽에서 드로어가 열린다.

## 드로어 크기

```text
width: min(86vw, 320px)
height: 100dvh
```

## 포함할 항목

상단:

* Moodi 워드마크
* 사용자 프로필 요약
* 새 기록 버튼

주요 메뉴:

* 오늘
* AI와 대화
* 모든 기록
* 캘린더
* 회고

보조 영역:

* 작성 중인 기록
* 최근 기록 3~5개
* 즐겨찾기

하단:

* 설정
* 데이터와 개인정보

## 동작

* backdrop 클릭 시 닫힘
* Escape로 닫힘
* 메뉴 선택 후 닫힘
* focus trap 적용
* 닫힌 뒤 햄버거 버튼으로 focus 복귀
* body scroll lock
* 화면 회전 후에도 레이아웃 유지

드로어를 데스크톱 사이드바 그대로 복사하지 마라.

모바일에서는 텍스트, 간격과 최근 기록 노출량을 줄인다.

---

# 7. 모바일 하단 네비게이션

모바일 핵심 메뉴는 하단 네비게이션으로 제공한다.

## 탭 구성

```text
오늘
기록
AI
캘린더
나
```

`AI`는 중앙 탭으로 배치할 수 있다.

단, 과도하게 큰 원형 버튼이나 강한 그라데이션을 사용하지 않는다.

## 작성 기능

기존의 `작성` 탭은 하단 메뉴에서 제거한다.

새 일기 작성은 다음 위치에서 접근할 수 있다.

* 오늘 화면의 주요 CTA
* 상단 App Bar의 새 기록 버튼
* 햄버거 드로어의 새 기록 버튼
* 기록 화면의 새 기록 버튼

이 방식으로 하단 메뉴를 5개 이내로 유지한다.

## 하단 네비게이션 규격

* 높이: 약 60~68px + safe area
* `env(safe-area-inset-bottom)` 반영
* 반투명 neutral surface 사용 가능
* 상단에 낮은 대비 경계선
* 터치 영역 최소 44px
* 텍스트 11.5~13px
* 아이콘 20~23px
* 활성 탭에만 accent 사용
* 비활성 탭은 충분한 대비의 secondary color

네비게이션이 페이지 콘텐츠와 채팅 입력창을 가리지 않게 한다.

---

# 8. 모바일 타이포그래피

모바일에서는 데스크톱 폰트 크기를 그대로 사용하지 않는다.

다만 모든 글자를 지나치게 작게 줄이지 않는다.

## 권장 스케일

```text
Display / 홈 핵심 문장:
30~36px / 650

페이지 제목:
26~30px / 650

에디터 제목:
30~36px / 650

기록 상세 제목:
28~34px / 650

섹션 제목:
18~21px / 600

카드 제목:
16~19px / 600

일반 본문:
15.5~17px / 400

일기 본문:
17~18px / 400

채팅 본문:
15.5~17px / 400

UI 라벨:
13.5~15px / 500

메타데이터:
12.5~13.5px / 400~500
```

## 규칙

* 입력 필드는 최소 16px를 유지한다.
* 일기 본문의 행간은 1.7 이상 유지한다.
* 채팅 답변의 행간은 1.6 이상 유지한다.
* 긴 제목은 2~3줄까지 허용한다.
* 설명 텍스트는 모바일에서 필요한 경우 줄이거나 숨긴다.
* desktop-only 장식 문구를 모바일에 모두 노출하지 않는다.
* `clamp()`를 사용할 수 있지만 min과 max 사이가 과도하게 변하지 않게 한다.

---

# 9. 모바일 spacing

모바일에서는 전체 간격을 단계적으로 줄인다.

```text
페이지 좌우 padding:
16~20px

앱 바와 첫 콘텐츠:
16~24px

섹션 간격:
28~40px

카드 간격:
12~18px

카드 내부:
16~20px

작은 컨트롤 간격:
8~12px
```

데스크톱의 48~64px 간격을 모바일에 그대로 적용하지 않는다.

그렇다고 모든 간격을 8~12px로 줄여 답답하게 만들지도 않는다.

---

# 10. 모바일 홈 화면

모바일 홈은 한 손 사용을 기준으로 다시 배치한다.

## 순서

1. App Bar
2. 날짜와 짧은 인사
3. 새 일기 작성 CTA
4. 빠른 기분 기록
5. 작성 중인 기록
6. 최근 기록
7. 오늘의 질문 또는 과거의 오늘

## 상단 영역

화면 절반을 차지하는 큰 hero를 사용하지 않는다.

첫 화면에서 다음이 보여야 한다.

* 현재 날짜
* 핵심 문장
* 새 일기 작성
* 빠른 기록 진입

## 최근 기록

* 한 컬럼
* 본문 미리보기 2~3줄
* 이미지는 16:9 또는 4:3
* 태그는 최대 1개
* 메타데이터를 한 줄에 모두 넣지 않음

---

# 11. 모바일 에디터

모바일에서 에디터가 가장 중요하다.

## 화면 구조

* 간결한 App Bar
* 제목
* 메타데이터 한 줄
* 본문 블록
* 모바일 편집 툴바
* 키보드 대응

## App Bar

```text
[닫기]         저장됨                 [완료]
```

추가 기능은 더보기 메뉴로 이동한다.

## 블록 편집

데스크톱 hover 핸들은 모바일에서 숨긴다.

블록 조작은 다음 방식으로 제공한다.

* 블록 탭 후 컨텍스트 메뉴
* 블록 왼쪽 또는 하단의 작은 메뉴 버튼
* long press
* 선택한 블록 전용 바텀시트

## 모바일 에디터 툴바

키보드가 열렸을 때 화면 하단에 표시할 수 있다.

지원:

* 블록 추가
* 텍스트 스타일
* 목록
* 사진
* 감정
* 키보드 닫기

툴바가 키보드와 하단 네비게이션에 동시에 겹치지 않게 한다.

작성 화면에서는 일반 하단 네비게이션을 숨길 수 있다.

## 키보드 대응

* `100dvh` 사용
* visual viewport 변화 대응
* 현재 입력 블록이 키보드 뒤에 가려지지 않음
* 저장 버튼이 접근 가능함
* iOS 자동 확대 방지를 위해 입력 폰트 16px 이상
* 키보드가 닫힌 뒤 scroll position이 비정상적으로 튀지 않음

---

# 12. 모바일 기록 상세

기록 상세 화면에서는 다음을 적용한다.

* 대표 이미지 full-bleed 또는 컨테이너 폭
* 제목은 28~34px
* 본문은 17~18px
* 좌우 padding 18~22px
* 메타데이터는 1~2줄로 정리
* 태그는 가로 스크롤보다 wrap 우선
* 수정과 삭제는 더보기 메뉴에 배치
* Moodi Note는 본문 하단에 한 컬럼으로 배치
* 관련 기록은 가로 carousel보다 세로 목록을 우선

---

# 13. AI 채팅 정보 구조

새로운 AI 채팅 페이지를 추가한다.

권장 라우트:

```text
/ai
```

기존 라우팅 규칙이 있다면 해당 규칙에 맞춰 조정할 수 있다.

## 페이지 목적

사용자는 AI 채팅을 통해 다음 작업을 할 수 있어야 한다.

* 특정 과거 기록 찾기
* 기간별 기록 요약
* 감정 변화 요약
* 특정 사람, 프로젝트, 장소 또는 주제 검색
* 비슷한 기록 연결
* 두 시기의 기록 비교
* 반복적으로 등장한 생각 확인
* 기록을 기반으로 회고 질문 받기

예시 질문:

```text
지난달에 프로젝트 때문에 힘들었던 날을 찾아줘.

이번 주 기록을 세 문장으로 정리해줘.

최근에 편안하다고 쓴 날들의 공통점은 뭐야?

작년과 올해의 학교생활 관련 기록을 비교해줘.

내가 자주 걱정한 주제를 찾아줘.

최근 한 달 동안 기분이 좋아진 계기가 있었어?
```

# 18. 기록 근거와 출처

AI 답변에는 사용한 기록을 확인할 수 있는 근거가 포함되어야 한다.

## Source Entry Card

각 근거는 다음을 포함한다.

* 날짜
* 기록 제목
* 본문 일부
* 감정
* 기록 열기

예:

```text
2026년 6월 17일
프로젝트를 마무리하면서

“해야 할 일이 없어서 오히려 막막했다…”
```

카드를 선택하면 해당 기록 상세로 이동한다.

## 규칙

* AI가 사용하지 않은 기록을 출처로 표시하지 않는다.
* 존재하지 않는 기록 ID를 만들지 않는다.
* 원문 인용과 AI 요약을 구분한다.
* 직접 인용은 실제 기록 텍스트에서 가져온다.
* 원문이 없으면 인용 부호를 사용하지 않는다.
* 출처가 없는 추론은 추론임을 명확히 표현한다.
* 검색 결과가 없으면 솔직하게 없다고 답한다.

AI 답변의 신뢰성을 위해 출처 카드 기능은 필수다.

# 20. AI 서비스 계층

UI 컴포넌트에서 AI API를 직접 호출하지 않는다.

다음 구조를 사용한다.

```text
AI Chat UI
→ AI chat hook 또는 use case
→ JournalAIService
→ Existing API / local adapter
```

예시 인터페이스:

```ts
interface JournalAIService {
  createConversation(): Promise<AIConversation>;

  getConversations(): Promise<AIConversation[]>;

  getConversation(id: string): Promise<AIConversation | null>;

  sendMessage(input: SendAIMessageInput): Promise<AIMessageResponse>;

  cancelMessage?(requestId: string): Promise<void>;

  deleteConversation(id: string): Promise<void>;

  renameConversation?(
    id: string,
    title: string
  ): Promise<AIConversation>;
}
```

응답 타입 예시:

```ts
interface AIMessageResponse {
  message: AIMessage;
  sources: JournalSource[];
  suggestedQuestions: string[];
}

interface JournalSource {
  entryId: string;
  diaryDate: string;
  title?: string;
  excerpt: string;
  mood?: Mood;
}
```

현재 프로젝트의 타입 구조와 충돌한다면 기존 타입에 맞게 조정한다.

# 21. AI API가 없는 경우

AI 백엔드가 아직 준비되지 않은 경우에도 UI와 서비스 경계는 구현한다.

단, 실제 AI가 동작하는 것처럼 거짓으로 표시하지 않는다.

가능한 방식:

1. 기존 기록에 대한 로컬 키워드 검색
2. 날짜와 태그 필터
3. fixture 기반의 UI 데모 응답
4. 명확한 mock adapter
5. 실제 API로 교체할 수 있는 service interface

mock 상태에서는 개발 환경에만 표시되는 작은 안내를 제공할 수 있다.

```text
개발용 로컬 검색 결과
```

프로덕션 화면에서 가짜 AI 답변을 실제 결과처럼 제공하지 않는다.

# 22. AI 검색 및 답변 안전성

AI는 다음 원칙을 따른다.

* 사용자의 기록만 근거로 답한다.
* 기록에 없는 사건을 사실처럼 말하지 않는다.
* 불확실한 내용은 불확실하다고 표현한다.
* 의료 진단, 정신 건강 진단 또는 치료 판단을 하지 않는다.
* 사용자의 감정을 단정하지 않는다.
* “기록상으로는”, “작성한 내용에서는”과 같은 표현을 사용한다.
* 민감한 기록은 앱의 잠금 및 개인정보 설정을 존중한다.
* 잠긴 기록은 사용 권한을 확인하지 않고 검색 결과에 포함하지 않는다.
* 삭제된 기록은 출처에 포함하지 않는다.

# 30. 모바일 레이아웃 자동 검사

Playwright에서 다음을 검사한다.

* `document.documentElement.scrollWidth <= viewport width`
* visible 요소가 viewport 밖으로 과도하게 나가지 않음
* fixed 요소 간 겹침 없음
* 하단 네비게이션이 콘텐츠를 가리지 않음
* 채팅 composer가 하단 네비게이션과 겹치지 않음
* 드로어가 viewport 밖으로 남지 않음
* 닫힌 드로어가 focus를 받지 않음
* 텍스트가 비정상적으로 잘리지 않음
* 입력 필드가 16px 미만이 아님
* 버튼 터치 영역이 최소 44px
* 캘린더 가로 overflow 없음
* 팝오버가 viewport 안에 위치함
* editor toolbar가 키보드 영역과 충돌하지 않음
* 이미지가 컨테이너를 벗어나지 않음
